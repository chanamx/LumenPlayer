**LumenPlayer 2.0.0 性能与内存复查 — 2026-10-23**

结论：仍有优化空间。最明确的是大播放列表的重复遍历，其次是播放控件的临时分配，以及关闭实时字幕时的主线程等待。字幕模型关闭后已释放主要占用；现有证据不支持“改几行就能无代价省下数百 MiB 常驻内存”。本轮只做检查与隔离测量，正式源码和发布程序未修改，以下数字均为当前实现的测量值，不是优化收益。

本轮沿用 Ponytail 的原则：先确认实际开销，再选择小范围修改；保留播放质量、兼容后端、字幕内容、音频队列的时间戳和拖动代际保护。之前已经落地的轻量播放状态快照、条件变量唤醒、静态选项表不重复列为待优化项。

测试使用当前源码单独编译的诊断程序、正式版本同一套 UCRT64 运行库和同一份字幕模型。播放测试运行两个独立进程，每个进行三轮打开视频、暂停、启用字幕、关闭字幕、关闭媒体；另有一个微基准进程和一个只含播放内核的六轮生命周期进程，四个进程均正常退出。媒体为本项目 `test/speech_test.mp4`，1280×720 H.264/AAC 短片，隐藏窗口尺寸 1120×700。完整播放路径实际报告 `d3d11va / gpu-next / wasapi`，每轮字幕阶段验证了至少三秒真实 PCM 输入，暂停状态也由内核确认。

这是源码诊断程序的短时测量，未直接测正式 EXE 的可见窗口帧率，也未覆盖 4K/HDR、网络直播、功放设备、全天播放或所有兼容后端。诊断程序插入了计时、内存采样和 C++ 临时分配计数；这些数值适合定位本次热点，不能当成跨设备性能承诺。没有进行前后版本 A/B 对照。

| 优先级 | 已确认的开销及触发条件 | 建议处理 | 体验与验证要求 |
|---|---|---|---|
| 高 | 导入大量 M3U/M3U8 条目时，为每个标题重新线性寻找对应条目；1 万条约 3.75 秒 | 复用或一次建立临时路径索引，避免嵌套遍历 | 保留本地路径忽略大小写、网络 URL 精确匹配、去重、标题覆盖和总量上限 |
| 高 | 列表很大、当前条目靠后时，绘制与命中判断反复寻找当前条目；1 万条的 `Controls()` 平均约 5.87 毫秒 | 一次绘制或交互中共享当前索引和控件结果，先避免重复求值 | 列表切换、移除条目、换媒体后状态必须即时正确；不引入容易失效的长期缓存 |
| 中 | 正常工作中的实时字幕停止耗时 232–408 毫秒，调用链同步等待模型线程完成尾句 | 评估让耗时的收尾在后台完成，主线程及时响应 | 需要单独验证最后一句、立即重开、拖动、退出及回调生命周期；不能直接跳过等待或丢弃结果 |
| 低成本 | 当前测试布局每次构造控件列表发生 38 次 C++ 分配，共申请 3,792 字节 | 字面量标签改用静态文本引用，减少临时字符串；复用本次控件结果 | 主要减少分配次数和临时开销，不能等同于同等大小的常驻内存节省 |
| 低 | 丢弃大量字幕时 `clear()` 保留数组容量 | 在真正丢弃旧媒体/旧字幕会话的边界释放容量 | 不要在暂停、拖动或仅关闭识别时丢弃仍可导出的字幕 |

大列表测量调用现有 `Playlists::Import`，输入在内存中预先生成，不包含下载、磁盘解析或网络访问。导入结果检查了条目数量和标题数量。控件测量将当前媒体设为列表最后一项，每组调用 300 次；这是较重的查找情形，不能套用到几十条的小列表。

原因可以直接对应到 [playlist.cpp:104](D:/LumenPlayer/src/playlist.cpp:104) 的导入流程：`AddMany()` 已使用映射去重，但标题处理再次逐条调用线性 `IndexOf()`。控件路径见 [main.cpp:277](D:/LumenPlayer/src/main.cpp:277)、[main.cpp:479](D:/LumenPlayer/src/main.cpp:479) 和 [main.cpp:1219](D:/LumenPlayer/src/main.cpp:1219)。这里的日常上一项/下一项可用性判断没有扫描文件是否存在，热点是重复的条目查找，不应误改成文件系统缓存。

内存使用 `PROCESS_MEMORY_COUNTERS_EX.PrivateUsage`，即进程私有提交内存；工作集另存于原始记录。它不等于实际物理驻留内存，也不包含完整的 GPU 显存占用。CPU 使用进程累计用户态和内核态时间除以墙钟时间，不是任务管理器对整机 CPU 的百分比。定义依据：[微软内存计数文档](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)、[微软进程 CPU 时间文档](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes)。

每轮关闭字幕后，前后阶段的内存均值下降约 217–228 MiB；六轮均检测不到已加载的 `onnxruntime.dll`。源码也确实销毁识别器、释放模型运行库、清空 PCM 队列，见 [captions.cpp:277](D:/LumenPlayer/src/captions.cpp:277)。这支持“主要模型占用已释放”，但不证明整个进程没有任何内存保留问题。切换关闭字幕后保留已生成的文字供导出是正常行为，关闭媒体后本次测试的字幕条目数均为零。

主线程停止字幕的六次测量为 264.25、231.90、314.28、407.50、280.92、353.96 毫秒，见 [main.cpp:620](D:/LumenPlayer/src/main.cpp:620)。这是正常识别工作中的停止耗时；模型尚在启动时提前关闭的等待时间没有在本轮测量。收尾要保留尾句，适合单独改造并验收，不能把“更快返回”当成已经完成资源回收。

为区分字幕与播放资源，补充诊断完全不创建 UI 绘制层、不加载识别模型，只创建和销毁播放内核。每轮在实际开始播放后取样，销毁内核后等待一秒再取样。

六次关闭后均检测不到 `libmpv-2.dll`，全程没有加载 ORT。残留在只含播放内核的进程中也出现，后四次约在 110–113 MiB，未表现为每次开关都等量增加。由此可把后续定位重点放在播放路径的分配器、依赖库和图形驱动资源保留；尚未证明具体归属，也未排除长时间缓慢增长。不能直接称为字幕泄漏，不能据此承诺可安全回收全部这部分内存，也不建议通过强制清空工作集制造较低数字。

长字幕检查还发现两个较小的空间。`SubtitleTrack::Append()` 每批重建索引，正常顺序追加时可以增量更新，乱序/回拖时维持完整重建。预置 1,000 / 10,000 / 50,000 条字幕后分别追加 200 条，总耗时为 0.41 / 3.01 / 24.79 毫秒，通常不是瓶颈。之后 `Clear()` 仍保留的字幕数组分别为 80,000 / 800,000 / 4,000,000 字节，未计索引容量，也不是实测进程可立即归还的内存。50,000 条若每三秒一条约对应 41.7 小时，属于很长会话，优先级低于大列表。位置见 [subtitle.cpp:198](D:/LumenPlayer/src/subtitle.cpp:198) 与 [subtitle.h:16](D:/LumenPlayer/src/subtitle.h:16)。

渲染仍有结构性空间：软件 UI 覆盖层发生更新时整幅重绘和上传，相关位置是 [main.cpp:1619](D:/LumenPlayer/src/main.cpp:1619) 与 [gfx.cpp:123](D:/LumenPlayer/src/gfx.cpp:123)。本轮字幕阶段整体 UI 绘制累计约 37–50 毫秒/秒，而字幕绘制函数在每个七秒阶段仅累计约 2.64–4.44 毫秒。字幕布局缓存的绝对收益目前很小，不能把 UI 总耗时都归给字幕布局。单个 3840×2160 的 32 位缓冲理论上约 31.64 MiB，这只是尺寸计算，不是本轮 4K 测量。若未来高分辨率实测证明该路径显著占用，再评估缩小绘制/上传区域；现在不建议为此重写整条渲染管线或降低交互刷新频率。

当前模型本身、播放帧缓冲和原生运行库占据主要内存。模型已经量化，音频输入队列已有上限，文字格式缓存也有容量限制。随意缩小解码缓冲、删除兼容库、频繁卸载再加载模型，可能影响拖动、弱网络和字幕响应。未获得同等效果的实测前，不把这些列作“完全不影响体验”的改动。低风险的实施顺序应是：导入和控件的重复查找 → 静态控件标签 → 明确丢弃边界的字幕容量释放；异步字幕收尾及播放内核保留内存另行定位、验证。
