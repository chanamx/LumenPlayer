## 3. 当前磁盘实测：需区分路径总长、共享文件和发行白名单

盘点使用 `st_dev/st_ino/st_nlink` 区分同一文件的硬链接，以 `GetCompressedFileSizeW` 查询数据占用，对 build 内不小于 50 MiB 的文件按独立文件身份执行 SHA-256。没有修改链接、压缩属性或文件内容。

| 范围 | 逻辑字节换算 | 去除本范围内硬链接重复后的数据占用 |
|---|---:|---:|
| 可读取工作区 | 38.564 GiB | 26.188 GiB |
| build | 34.484 GiB | 22.961 GiB |
| .rustup | 2.094 GiB | 2.094 GiB |
| .cargo | 0.350 GiB | 0.350 GiB |
| third_party | 1.183 GiB | 1.183 GiB |
| 完整 dist：152 个文件 | 363.819 MiB | 235.145 MiB |
| 正式发行白名单：111 个文件 | 204.973 MiB | 110.272 MiB |

目录之间可能共享文件，因此各目录“去重后占用”不能再直接相加作为工作区唯一占用。字节查询不含目录/MFT 等文件系统元数据，也不等于删除某个目录能释放的字节。盘点排除了本次审计目录；11 个权限拒绝子目录未读取，10 个测试用目录联接未跟随，故工作区总量是可读取范围的下限。正式发行 111 个文件的身份校验完整通过。

空间方案最需要修正的地方：

1. **“同名同大小的实际可去重量只会更高”不成立。** 同名同大小可能内容不同，也可能已是同一硬链接文件。当前 build 中，仅既有硬链接已避免约 **10.430 GiB** 的重复路径数据占用。
2. 不小于 50 MiB 的 build 文件有 132 个路径、96 个独立文件身份；同名同大小的路径冗余约 **11.246 GiB**。按 SHA-256、已有链接、范围外仍保留的文件身份核算，剩余大文件的**物理去重上限约 4.423 GiB**。这是忽略可写性等限制的上限，不能当作已确认可回收量，也未涵盖小文件或权限拒绝目录。
3. 文档提到的 Hy-MT2 大 GGUF，当前 **5 个路径已共享同一文件身份**，对这组再次“去重”可回收 0 字节。Index 的两个路径同样已共享；NanoSakura 部分副本也已共享。
4. 当前无模型发行载荷的数据占用约 110.27 MiB。225 MiB 属于旧版含模型目录口径，不能继续作为当前无模型发行目录的起点。完整 dist 仍含 155.616 MiB 逻辑大小的旧中文模型；该用户模型的数据占用约 121.645 MiB。
5. 当前 **110/111 个发行文件还与 build 中测试/QA 副本共享文件身份**，EXE 为单独文件。硬链接不是目录依赖，删除一个链接不会让另一个失效；但原地覆盖或修改压缩属性会影响共享对象。不能宣称 dist 所有文件在物理上独立，也不能将这些共享对象再次记为清理收益。正式文件内容校验仍全部通过。
6. dist/cache 约 3.124 MiB，已不在发行白名单内。每次发布清空它不会减小现行安装包，却可能增加首次渲染编译开销；不符合优先保启动速度的目标。

## 4. 参数和内存推断核验

| 方案中的判断/建议 | 当前证据及需要修正的结论 |
|---|---|
| 本地 demuxer 缓存改小可省 20–40 MB | 64/16 MiB 上限确实存在；但当前 `cache=auto`、普通 readahead 为 1 秒。固定版本手册表明网络/慢源才按启发式启用 cache，普通本地文件并非必然填满 80 MiB。必须记录实际 demuxer cache 后判断，不能将配置差额当成内存收益 |
| `vd-queue-max-*` 可减少 4K/软解 10–50 MB | 固定正式 DLL 实际返回 `vd-queue-enable=no`、`ad-queue-enable=no`。该额外队列当前没有启用；修改其上限没有这项默认收益，也不能把它和解码器内部参考帧/硬件帧混为一谈 |
| 解码线程统一封顶 4 | 当前为自动选择 `vd-lavc-threads=0`；固定手册的自动选择已有最多 16 线程边界。降到 4 需要按软件解码场景测量吞吐、掉帧和首帧；不能作为不影响体验的默认优化 |
| libplacebo cache 16→4–8 MiB 可省 8–12 MB | [video_bridge.cpp:21](D:/LumenPlayer/src/video_bridge.cpp:21) 的值是上限，不是预分配。固定头文件提供 `pl_cache_size`/`pl_cache_objects`，应先记录实际占用。本 cache 属于兼容视频桥，不能直接外推现代 mpv gpu-next 路径的所有 GPU/CPU 缓存 |
| PCM 3 秒/16 MiB 减半可省 4–8 MB | [mpv_backend.cpp:243](D:/LumenPlayer/src/mpv_backend.cpp:243) 三个条件共同限流，并未预分配 16 MiB。48 kHz 双声道 float 的 3 秒仅 1,152,000 B，即 1.099 MiB；减为 1.5 秒最多减少 576,000 B，即 0.549 MiB 的音频数据，且只有原队列填满时才可能达到。高采样率/多声道另计 |
| ASR 输入队列有大量空间可缩 | 归一化后的 ASR 队列已经限制为 2 秒、16 kHz 单声道 float，数据上限 128,000 B；不能把上游安全上限算到这里。缩短还可能在忙时增加丢输入，优先保识别连续性 |
| 4K 软件覆盖层约 31.64 MiB | 尺寸计算正确；[gfx.cpp:85](D:/LumenPlayer/src/gfx.cpp:85) 确实创建整窗 32 位 DIB。但目前没有当前 4K 联合负载对照，释放/缩小需验证隐藏字幕、控制条唤醒、全屏和 DPI，属于后续实验 |
| 缓存字幕文本布局 | [main.cpp:1478](D:/LumenPlayer/src/main.cpp:1478) 仍每次创建布局，候选成立。缓存键需覆盖文本、宽度、字号、字体/DPI和绘制工厂生命周期。主要是重复计算/临时分配收益，不能承诺数十 MB 内存或明显帧率增长 |
| `LiveCaptions::Stop` 再统一 swap 容量 | queue 已 swap；真正丢弃会话时 `ClearResults` 和 `SubtitleTrack::Clear` 已释放数组容量。pending finals 在 Stop 后还要交给主线程保留尾句；直接清空会丢结果。它也不是随整部长片累计的字幕库，剩余容量优化应放在结果收集完毕之后 |
| ORT 再关闭内存模式/启用顺序执行 | NanoSakura 已是单线程、顺序执行、CPU arena 关闭。Zipformer 的配置只在内容逐字节等于 `EnableCpuMemArena=0\n` 时才启用，直接追加 `EnableMemPattern=0` 会使当前整份自定义 provider 配置不再使用。必须先做受支持键和启动解析实验，不能只改配置文件 |
| NanoSakura 初始状态缓冲复用 | 每句两块初始 float 缓冲合计 9,695,232 B，即 **9.246 MiB**，当前重复分配属实。复用可减少分配/清零抖动，但会在会话内保留缓冲；不能直接算作同等大小的常驻内存下降。也可研究首步后不再使用的初始缓冲是否能更早释放，须遵守 OrtValue 引用生命周期 |
| 翻译 Job 3→2 GB 可降低总内存 | 当前是 `JOB_OBJECT_LIMIT_PROCESS_MEMORY`，限制子进程私有提交，未设置整个 Job 的总内存上限。它不限制全部文件映射驻留页、整个播放器树或 GPU 显存；调低限额也不等于实际用量下降。应测进程树并保留分配失败后的原文/错误恢复 |
| 超过 Job 内存上限会被直接杀死 | API 的直接语义是超限提交失败；运行库可能随后失败或退出。`KILL_ON_JOB_CLOSE` 则是关闭最后 Job 句柄时终止成员。这两种机制应分开表述 |
| NanoSakura 子进程化可使主进程下降 100 MB 级 | 隔离和可强制退出方向成立，但这是把模型移到另一个进程。总内存可能不变或增加，并有 IPC/启动成本；不能把主进程变小算成整机省内存，当前没有本机前后对照 |
| 翻译空闲卸载、ASR/播放内核统一代理 | 会增加下一句或下次打开的冷启动成本。用户更重视实时性，建议保持非默认、待实测方案；当前只证明存在历史残留，未定位可安全回收的具体归属 |
| 176/400 MiB 等历史数据可定当前目标 | 它们确实来自 2.0 的 720p 短片测量，但模型、功能和版本已有变化。145–155/330–350 MiB 应保留为未经验证的研究目标，不能作为当前版必达值或已确认收益 |

内存术语也需小修：`WorkingSetSize` 是当前工作集，反映当前驻留的可分页物理页，包含可共享页面；`PrivateUsage` 是私有提交，不能当作物理驻留。这两项都不能独立代表全部进程树及 GPU 用量。依据为 [Microsoft Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)、[PROCESS_MEMORY_COUNTERS_EX](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)。Job 限制语义见 [EXTENDED_LIMIT_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information) 和 [BASIC_LIMIT_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)。

mpv 参数先通过 Context7 查官方资料，再与项目固定源码归档及实际 DLL 对照。固定归档 SHA-256 与 provenance 相同，为 `6191718245e605686cffab293e6db2ba1bf164eb14e9043974ff8e4aa286c491`。实际选项记录见 [candidates.json](D:/LumenPlayer/build/optimization-verification-20261029/candidates.json)，固定手册核对见 [fixed-options.json](D:/LumenPlayer/build/optimization-verification-20261029/fixed-options.json)。该 DLL 探针不加载媒体，使用 null 输出，仅证明选项状态；不证明播放性能或内存下降。
