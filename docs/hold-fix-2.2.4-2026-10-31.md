# LumenPlayer 2.2.4 长按倍率修复

问题原因：2.2.3 的 `FastForwardRate()` 只在键盘 → 长按时读取设置的 `holdRate`。鼠标按住画面走另一套 `ffStage` 分段逻辑，初始固定 2 倍，约 1.1 秒后改为 4 倍，约 2.2 秒后改为 8 倍，与保存的倍率无关。未修改的 2.2.3 在新原生探针中复现了设置 1.25 倍、后端却收到 2 倍的失败。

本轮统一两种输入的倍率来源，删除分段状态、升档函数和定时调用。鼠标长按及启用的键盘 → 长按均使用设置值，支持既有 1.25–8 倍范围及 0.25 步进。持续按住不会自动升档；松开或取消时恢复长按前的正常播放速度与播放／暂停意图。无法直接变速的兼容路径仍使用定位回退，但每次定位步长也按设置倍率计算。

设置行改名“长按倍率”，键盘 → 开关只控制键盘长按。关闭该开关后，倍率仍可编辑，供鼠标长按使用。帮助文案与 README 移除了旧“2／4／8 分段快进”描述。2.2.3 的单击／双击互斥逻辑继续保留。

## 验证与额外发现

原生倍率矩阵覆盖 1.25、3.25、6、8 倍，鼠标／键盘，原先播放／暂停，支持变速／定位回退，以及恢复原先 1.5 倍正常速度。按下时间受控，检查 0.4、1.2、2.4、5、30 秒的逻辑时间点，覆盖旧升档边界；不是 30 秒实际墙钟播放性能测试。还运行实际现代核心的视频长按、倍率状态及松开恢复检查。

扩展混合后端测试发现了旧模式切换问题：兼容播放加载的 FFmpeg 可以比 libmpv 活得更久。现代核心卸载后，FFmpeg 的全局默认日志回调可能仍指向被卸载模块的 Windows 导入跳板。混合控件场景出现访问异常；另用本轮备份的原始 2.2.3 生产源码构建最小切换探针，确认核心已卸载后直接调用 FFmpeg 日志不能返回，最终由 80 秒保护终止。原始异常、调试模块记录、超时及源码快照均保留，不计为通过。

本轮在最后一个现代核心 API 实例退出时，将回调安全恢复为 `avutil-61.dll` 实际导出的默认函数，然后正常卸载核心。实例计数及模块装卸共用互斥保护，不干扰仍活跃的核心实例。修复后，同样的卸载后日志调用和“兼容→现代→兼容”切换均通过；未采用常驻保留整个播放核心的策略。
