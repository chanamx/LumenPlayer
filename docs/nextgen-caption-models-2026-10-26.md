# 新代际实时字幕模型与多源交付实测补充

检验日期：2026-10-26。本文补充[上一轮验证报告](D:/LumenPlayer/docs/verification-and-model-options-2026-10-26.md)，按本轮新增要求优先筛选 **2026 年起实际发布或经过实质训练的新模型**。代码维护、会议接收、格式转换、量化打包的日期单独记录，不能替代模型代际。

**目前的选择方向**

现有中文 Zipformer CTC 继续作为默认识别模型。2026 Moonshine Streaming/v2 的中文 Tiny 在本机显著节省 CPU 和内存，但现有口语标注样本出现重复和补字；英语、日语、德语 Tiny 值得保留为按语言下载的接入候选。统一多语种 Nemotron 3.5 已实际运行中、英、日、法、德，但所测 Windows CPU 路径远超当前中文模型的内存预算。

文本翻译保留 **Index-Translate 2B（2026-09，多语覆盖优先）**和 **Hy-MT2-1.8B（2026-05，内存取舍较好）**两条专用模型路线，均有本机完整测试。LFM2.5 的被测低比特版本出现了可复现的数字和动作错译。Index 的文本模型与需要更多音频组件的 Index-Echo 分开评价。上述组件测试尚不能证明播放器完整播放、识别、翻译、显示链路的最终延迟。

Whisper tiny、原始 SenseVoice、2025 Kroko、OPUS-MT 等只保留为旧基准。NiuTrans LMT-60-0.6B 的仓库建立于 **2025-11-09**，[论文首版亦为 2025-11](https://arxiv.org/abs/2511.07003)；2026 年修改和 ACL 接收不能独立证明一个 2026 新训练代际，因此未列入优先方案。LFM2.5、Hibiki-Zero 等虽然沿用较早架构，却有明确的新训练证据，属于不同情况。

**多源交付：实际取得了什么**

本轮补齐了既有中文模型的官方 GitHub 归档：**127,965,713 字节**，SHA-256 为 `f2ab7a5deb02717801f6a5b26c751b42f8a2db891b07f5b095e6da7442081448`。归档内部两件关键文件继续逐项核对：

- `model.int8.onnx`：162,290,887 字节，SHA-256 `24ffdc19ba9aaed5a6a9beaede1e087745217d82425cf4041bca0c696661801e`。
- `tokens.txt`：20,628 字节，SHA-256 `6193c7ea1c96d0d9a1e9652789b40d13a8a913b434a5451e93158f5a09fd6652`。

二者与上轮取得的 HF/当前标准文件一致，权重也与上轮魔搭镜像权重相同。**魔搭该旧中文镜像的 tokens 与标准文件不一致**，仍须按标准摘要管理权重和 tokens 配对，不能把整仓库无条件混用。该魔搭镜像是社区发布者；平台名称不等于模型作者背书。

**实测口径**

本机为 i5-7200U、约 8GB 内存。识别测试用真实原生推理库，按 16kHz 单声道 PCM、200ms 块模拟播放速度送入；持续测试以同一来源音频重复至 60 秒并插入短静音。重复数据用于检查持续时延与资源，不算新增独立语料。静音和低电平噪声另列，不混入语音 CPU 中位数。

“CPU 秒/音频秒”是进程累计 CPU 时间除以音频长度。它是运算成本；多核配置可大于 1，不能仅凭该值判断墙钟是否实时。出字延迟、最大落后时间及块耗时单独保留。识别首字从模型就绪后开始送音频起算，不含加载阶段。

Moonshine 使用单线程 ORT。Nemotron SDK 未暴露线程数控制，测试使用 **1 或 4 个逻辑处理器亲和性上限**，不能称为“SDK 单线程”；均关闭批处理、请求一份状态 arena，右上下文为 6（算法步长 560ms）。两者运行配置有区别。当前模型基准来自上轮同机 C++ 探针，Moonshine/NeMo 测量还包含 Python 探针自身开销，适合预算比较，不是严格同构性能榜。

翻译统一用本地 llama.cpp `b11889` CPU、1 个推理线程、1 个槽、上下文 1024。测试文本覆盖中英双向、日法德到中/英、英到日法德以及时间、数量、否定、歧义、惯用表达。翻译首字和整句耗时都从**完整输入文本到齐**开始；原始结果里的 4/8 秒预算只是示意任务到达间隔，不是实录音频时长，也不是识别加翻译的整链路成绩。

内存同时记录私有提交与工作集。例如 Nemotron 的工作集约 1GiB，但私有提交约 3.47GiB；不能只用其 708MiB 左右的 GGUF 文件或当时物理工作集代表总资源压力。

现有 WenetSpeech DEV0 的固定标注只有 **29 个字符**。在这一个样本中，现有 CTC 是 1 个编辑、CER 3.45%；Moonshine 中文 Tiny 是 9 个编辑、31.03%，在两种 ORT 路径和重复运行中均出现：

> 对我做了介绍对我做了介绍……大家如果对我的研究感兴趣呢你一定

与现有标注相比，存在开头重复和尾部补字。Nemotron 在同样本也是 1 个编辑。此结果足以让当前中文默认保持谨慎，却**不能外推为整个模型的全语料 CER**。

两个英语 LibriSpeech 样本合计 66 个参考词。相同规范化规则下：Tiny 为 4 个编辑，Small 0.5s 更新同为 4 个，改 1.0s 更新为 5 个，Nemotron 为 3 个；拼写及复合词分词差异也计入。样本很小，不能据一两个编辑声称整体准确率领先。法语的三个 Common Voice 样本有 35 个参考词，Nemotron 为 5 个编辑，专名与时态仍有错误。

中文、日语的 60 秒重复流均保持了资源余量；被测静音及低电平噪声没有生成文字。这不替代电影、音乐背景、多人重叠、口音和高噪声语料测试。尝试取得更多 FLEURS 行与样本时，官方查看服务返回 500/501，该数据没有进入成绩。

**翻译结果**

| 被测配置 | 独立文本 / 总次 | 首字中位 | 整句中位与范围 | 峰值私有提交 / 工作集 |
| --- | --- | ---: | --- | --- |
| Hy-MT2-1.8B Q4_K_M，默认重排 | 20 / 40 | 1.57s | 3.07s；1.96–5.19s | 949 MiB / 1.92 GiB |
| Hy-MT2，同权重关闭重排 | 20 / 20 | 2.16s | 3.88s；2.05–5.78s | **224 MiB / 1.21 GiB** |
| LFM2.5 QAD-Q4_0，作者建议温度/Top-k | 20 / 20 | 1.49s | 2.28s；1.80–3.83s | 651 MiB / 1.26 GiB |
| Index-Translate 2B Q4_K_M，关思考/重排，默认服务缓存 | 20 / 20 | 2.28s | 3.50s；2.93–5.92s | 769 MiB / 1.72 GiB |
| Index，同权重另禁用提示缓存与上下文检查点 | 20 / 40 | **1.97s** | **3.21s；2.62–5.35s** | **355 MiB / 1.32 GiB** |

Hy-MT2 关闭权重重排后，峰值私有提交减少约 76%，工作集减少约 37%，整句中位耗时增加约 26%。这提供可用的低内存取舍，但仍有约 1.2GiB 的工作集，不能把“224MiB 私有提交”解读为总共只占 224MiB。

Index 初次连续请求时，私有提交由约 375MiB 增至 769MiB，不能把这张表当成长期稳定占用。检查本机可执行程序帮助与 [llama.cpp 服务端文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)后，另一组测试显式设置 `--cache-ram 0 --ctx-checkpoints 0 --no-cache-prompt --no-cache-idle-slots`，仍保留关闭重排与思考。40 次请求中，首条完成时约 352MiB，末条约 354MiB，峰值约 355MiB，未再出现前一配置下的明显逐请求增长。对照支持这一配置组合的效果，未逐项分离各缓存层贡献，也不将 40 次测试等同无限期零泄漏。

Index 正确保留了本轮十五分钟、周四 14:30、120 欧元不含早餐、两间房住三晚及改期等样本的关键数字与否定，覆盖面更广；日语短句“次の信号を左に曲がってください”仍译得生硬，河岸歧义句也选成“银行”。因此它是值得进入真实字幕链路验收的新代际候选，不是已经取得通用翻译准确率保证的正式替换。

Hy-MT2 在本轮数量、否定及中英互译样本中相对稳定，例如正确保留“周四 14:30，不是周五”“每晚 120 欧元、不含早餐”“两间房、三晚”。歧义样本仍会把河岸语境中的 `bank` 选为“银行”，日语路口句的表达也未必最精确，不能声称已通过通用字幕质量验收。

LFM2.5 被测 QAD-Q4_0 在贪心和作者建议的 `temperature=0.1、top_k=50、repetition_penalty=1.05` 下均出现：

- 法语“十五分钟后出发”变成“十五分钟后到达”。
- 德语同义句变成“五十分钟后到达”。
- 日语驾驶指令变成“将下面的信号转向左侧”。
- 作者建议参数下，“两间房住三晚”又变成“三间房住三晚”。

因此当前被测低比特版本不列为默认翻译器；此判断不等于给整个 LFM 系列或更高精度版本下结论。

Hy-MT2 官方还有约 440MiB 的 1.25-bit 权重，但其卡片指向的 [STQ 专用内核 PR](https://github.com/ggml-org/llama.cpp/pull/22836) 在核验时仍开放，主要展示 ARM NEON 性能。该文件的大小和渠道元数据已经核对，Windows x86 上的完整性能没有验证，不能拿它替代本轮 Q4 成绩或承诺相同速度。

**直接语音翻译与落地边界**

[Qwen3.8-LiveTranslate](https://qwen.ai/blog?id=qwen3.8-livetranslate) 是较新的云端备选。作者公布 2.3s LAAL、60 种输入/文本语言及源文/译文同步等能力；LAAL 与本表的首字或文本生成时间定义不同。这是作者的云端成绩，本轮没有账户、网络及费用环境下的实测，也没有把云端计算称作本地低耗模型。

[Hibiki-Zero](https://kyutai.org/blog/2026-02-12-hibiki-zero/) 确有新训练和流式语音到语音/文字翻译，但当前公开方向仅为法、西、葡、德到英语。[Index-Echo S2TT 2B](https://huggingface.co/IndexTeam/Index-Echo-S2TT-2B) 的公开接口主要是中文到英/日/西，默认按较长窗口处理；作者给出 bf16 约 10GB 显存参考，而且 GGUF 仅有语言骨干时还缺音频编码器与连接器。二者都不能直接当作当前五语低消耗实时互译方案。

本轮完成的是来源完整性、原生组件运行与预算测试。播放器正式接入还需要模型选择与语言路由、权重/词表原子管理、下载取消恢复、seek/倍速/暂停时的字幕时序、翻译队列以及真实播放下的联合资源验收。现有正式 EXE、播放内核、模型和安装包的 28 项关键基线仍逐一验证不变。上轮约 60.7MiB 的无模型安装包是验证构建，正式分发切换仍是独立发布工作。

本轮共有 **40 次成功的独立识别进程测量**，另有一次作者 CLI 功能核对；文本翻译共有 **155 次请求**，反复使用同一组 **20 条独立文本**比较模型和运行配置。识别输入覆盖 10 个不同语音文件及重复、空白、噪声夹具，不能把进程数或请求次数写成同等数量的电影、说话人或独立语料。所有推理任务逐个执行，提交余量保护没有触发内存不足中止；[进程清理记录](D:/LumenPlayer/build/models-nextgen-20261026/process-cleanup.json)确认本轮辅助进程已经全部退出。
