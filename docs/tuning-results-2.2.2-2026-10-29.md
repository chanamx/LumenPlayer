# LumenPlayer 2.2.2 实际优化与验证

本轮在 2.2.1 正式版本上实施了已确认的优化候选。保留固定 UCRT / libmpv / FFmpeg / ONNX Runtime、现有解码与协议支持、模型精度、推理线程及播放缓存策略。源码、正式发布和本次证据由 `test/finalize_tuning_release.py` 统一核对；发布状态见 `build/tuning-20261029/publication.json`。

## 已实施的改变

| 改变 | 目的与实际行为 | 成本及边界 |
|---|---|---|
| 模型安装空间预检 | 在现有后台下载线程中，先查询目标目录所属卷对当前调用者可用的空间；计算剩余下载量、解包/解码峰值、备用源回退及 64 MiB 余量。已完整校验的暂存文件和普通 `.part` 可抵扣相应下载空间。空间不足时提前提示，保留旧模型和续传数据。 | 不额外增加启动轮询或推理进程；安装时多一次空间查询，完整暂存文件沿用 SHA 校验。空间预检不能预留卷容量，其他进程仍可能随后占用空间。 |
| 成功安装后的缓存收尾 | 安装原子切换成功后，按模型目录清单清理 `.part`、压缩包、已解码 tar、提取成员和空目录。安装删除逻辑共用这份清单；未知文件、未知目录及用户数据保留。 | 失败或取消仍保留续传能力；清理失败显示提示，不撤销已成功安装的模型。没有对用户已有目录做一次性泛清理。 |
| NanoSakura 初始状态缓冲生命周期 | 初始卷积和 SSM 状态改由 ORT 默认 CPU 分配器持有，第一步解码释放旧 OrtValue 时即可释放初始缓冲，避免额外的零向量一直存活到整句结束。 | 保留状态形状、零值、模型、分词、最大输出、取消规则、精度与线程数；只影响日译中 NanoSakura 路径。 |
| 压缩辅助工具与无模型发行一致 | 按根目录发行清单选择已知 DLL；旧式识别模型目录存在时才纳入，保持不完整目录、链接逃逸和共享文件的保护。未知 DLL、托管用户模型不纳入。 | 继续使用 XPRESS8K；支持恢复与逐文件哈希核对。 |
| 不可变开发副本去重 | 三个明确的非活动历史测试运行目录中，90 份单独存储的 DLL 与固定来源逐个核验后，原子替换为同内容硬链接。 | 排除正式发布对象、模型、设置、恢复包和安装验收载荷；保留原目录与全部内容。受支持的后续构建通过原子替换写文件，不原地覆盖共享对象。 |
| 验证入口更新 | 将错误停留在 2.0.0 的 `docs/core-validation.md` 改为当前版本索引，并保留历史报告入口。 | 旧断言、旧性能数字继续归属原构建。 |

生产 C++ 本轮净增加 66 行，新增依赖 0。增加的代码主要用于安装空间保护和缓存清单共用；没有把行数减少作为收益，也没有引入新的后台模型代理。

## NanoSakura 同版本基线实测

基线使用修改前的 2.2.1 源码，候选使用本轮源码；固定同一份 NanoSakura INT8、同一组日文输入及相同运行 DLL。每版各三次新进程，交替顺序运行；未清空系统文件缓存，因此不称为冷启动测试。内存采样为进程私有提交量，不能直接解释为物理内存占用。

| 指标 | 2.2.1 基线 | 2.2.2 候选 | 结论 |
|---|---:|---:|---|
| 翻译活跃期间私有提交量，三次中位数 | 619,585,536 B | 610,799,616 B | 减少 8,785,920 B，约 **8.38 MiB** |
| 固定 8 句总翻译时间，三次中位数 | 13,291 ms | 13,422 ms | 候选约 +1.0%，样本范围重叠；没有测出提速 |
| 模型加载时间，三次中位数 | 3,362 ms | 3,531 ms | 加载代码未改变；存在运行波动，不宣称启动提速 |
| 独立完整输入集 | 20 句 | 20 句 | 所有原文和译文字符串逐项相同 |

原始记录：`build/tuning-20261029/nano-comparison.json`、`baseline-quality.json`、`updated-quality.json`。这次收益是局部缓冲生命周期缩短，不能推广为所有播放器进程、所有模型或长期会话都节省同样内存。

日语短视频也分别在两版实际播放路径运行：两版均收到 85,504 帧 PCM，生成相同的一条日文原文和中文译文，实际绘制中文、导出双语字幕、跳转清空旧译文并释放模型 DLL，各通过 13 项检查。首次译文在音频输入开始后分别约 10.47 / 9.25 秒返回；这是各一次、包含首次模型校验和初始化的观察值，不作为速度提升结论。片尾媒体时钟已经停住，JSON 中的 `mediaLagSeconds` 不能当作连续播放的真实译文延迟。

首次沿用旧探针时，两版都在片尾四秒后退出，最后一句的翻译尚未完成。保留了原失败记录；测试改为在原有总时限内等最后一句处理完成并记录事件，产品播放逻辑没有增加等待。另保留了测试暂存模型安装标记被 CRLF 改写导致识别未启动的失败，修正为与生产格式相同的 LF 后再验收。

## 空间与未采用的实验

历史测试运行目录的 90 份 DLL 去重，删除的独立已分配文件数据为 **544,051,881 B，约 518.85 MiB**。卷空闲空间同时增加 544,247,808 B，约 519.03 MiB，包含文件系统分配差异及同时段其他活动，收益以逐文件独立对象核验为准。这是开发工作区的回收量，不能计入安装包减小或播放器常驻内存。记录为 `dedup-applied.json`，并通过七项去重/原子重建保护测试及原有暂存构建检查。

字幕和 Toast 布局缓存做了独立实验：九个文本、宽度、比例和字体重建场景的像素指纹一致，500 次重复绘制的 CPU 中位数从 1,843.75 ms 变为 1,828.125 ms，只差一个计时量级，约 0.85%；墙钟差约 1.4%。收益不足以支撑新增缓存和失效逻辑，**已撤回该实验**。实验二进制、源码和测量单独保存在 `experiments/layout-cache`；生产 `main.cpp` 只修改版本文字。

没有缩小解复用/解码缓存、限制解码线程、清空 shader 热缓存、缩减编码器/协议或改用 LZX。以上项目需要冷/热启动、真实媒体和设备矩阵支撑，不能仅凭磁盘压缩比改变默认行为。保留 XPRESS8K。

同一份 111 文件载荷的安装压缩对照：

| 压缩级别 | 安装包字节 | 构建时间 | 受控构建进程树提交量峰值 |
|---|---:|---:|---:|
| lzma2/normal | 68,318,234 B | 70.91 s | 64,135,168 B，约 61.16 MiB |
| lzma2/max | 66,510,466 B | 99.78 s | 135,622,656 B，约 129.34 MiB |

采用 `lzma2/max`：相同载荷减少 1,807,768 B，约 **1.72 MiB / 2.65%**；成本是构建多约 29 秒、构建进程树峰值多约 68 MiB。进程树包含测试 Python 父进程、ISCC 和独立压缩子进程，保持编译器默认线程策略，有独立 Job Object 内存上限。这是压缩参数的同载荷对照，不能与旧版不同 EXE 的体积变化混算。运行文件内容不会因为安装包压缩级别改变。

## 发行与可复核入口

发布版本为 **2.2.2**，EXE 1,505,792 B，比 2.2.1 增加 6,144 B。111 个发行文件中只有 EXE 内容变化，其余 110 项 DLL、目录清单、着色器、许可证及依赖来源保持相同哈希。修改前 235 个自有文件已保存在 `before/2.2.1-recovery.zip`；正式目录的 58 个设置、列表、模型、缓存及其他用户文件另有保护清单。

正式安装包：`build/tuning-20261029/installer/LumenPlayer-2.2.2-x64-setup.exe`，66,510,466 B（约 63.43 MiB），SHA-256 `051916dcafb86aef5ae723b9a8b79ed9a07b83ed21704ff32a861034d08a708f`。EXE SHA-256 `eac92e6e7bc9f59fe29fbbc13728654843f49f2591a9bcc3043e6c65df45aa3a`。正式安装包与同载荷 max 对照产物的哈希一致。

实际静默安装 2.2.1、升级到 2.2.2、核对 111 个运行文件、运行安装后的正式 EXE、再卸载已通过。安装路径包含中文和空格；17 个测试用户文件，包括设置、列表、未知模型、实际 NanoSakura 模型、旧识别模型和手动保存字幕，在升级及卸载后均保留。实际播放使用 `gpu-next` / WASAPI / 同会话 PCM，收到识别结果；退出时丢弃 2 条未保存字幕，没有自行写出字幕文件。测试恢复原始 INI 和列表的字节内容。使用隔离 AppId，未验证系统快捷方式、注册表集成或人工点击向导。
